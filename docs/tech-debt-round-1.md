## 七、本轮沉淀的规则

### 门禁设计

1. **门禁只能由「答案由数据决定」的比较构成**；需要人解释"算不算"的检查进不了门禁。
2. **门禁的正确性上限 = 设计者选对了比较对象**，这一步无法被门禁保护。
3. **例外若源于真实缺陷 → 修缺陷不加例外**；**缺陷修好后，为它开的例外必须同步撤掉**（两条是同一件事的两端）。
3b. **两类例外必须分开管**，判据是「**这条异常会不会因为我改代码而消失？**」
   - **会 → 缺陷豁免**：必须有撤销触发器（修复该缺陷的提交内同步删除例外）
   - **不会 → 类别排除**：不适用触发器，但必须写明排除的**来源正则**（如 `/^\[\.WebGL-/`）
   - 混为一谈的后果不是例外变多，而是**规则信用被一条不可撤的例外击穿** —— 执行者会得出"这条规则做不到"，然后连真该撤的也开始不撤。
3c. **判据按类判，不按实例名列举**：按名列举的判据每加一个实例就要改一次，而"改判据"本身没有触发器。
4. **正向断言须配反向断言**（A/B 成对）；否则退化解可通过。
5. **每条断言双向校准**：① 正确实现上必须绿（防假红）② **落在同一链路上的**坏实现上必须红（防空转）③ **变异与该断言无关时，绿不构成"断言空转"的证据**（防误杀）。
6. 断言值必须**可满足**，且**不得在正确实现上为假**。
7. 计数口径必须声明（行 / 次）；数字须带三标签（单位 / 压缩状态 / 测量口径）。

### 判定与归因

8. **"判不了"是合法结论，"大概没问题"不是。**
9. **归因的判据只能是"分离变量"，不能是"看 stack 落在谁家"。**
   **出错位置与成因位置可以不在同一个文件、同一层，甚至不在同一方（自家 / 第三方）。**
   - 本次实例：`PreloadScene.ts:51` 是自家文件，单看它会归因错 —— 真正变量是 `BattleView` 的 effect 双执行；
   - 定案靠的是「去掉 StrictMode → 0 条」这个变量分离，不靠 stack 归属。
10. **来源须口径不同才算独立**；多来源一致 ≠ 独立。
11. **grep 的输出是"出现"不是"含义"**；推断含义必须打开原文。
12. **替代方案优于约定**：让那种错误写不出来 > 加注释 > 加断言 > 要求注意。
13. **"这样做会出错"必须能写成会红的测试**，写不出来就是猜测。

### 认知

14. 推理的有效性取决于**锚定**：对自己已说出口的结论推理命中率极低；对他人未锚定方案有效。处方 —— 结论对外前换前提重推；已说出口的只能靠未锚定第二人从零重搜。
15. **在写「X 已被 Y 覆盖」前，先各写一行「X 问：……？Y 问：……？」，第三人判读；判不了 → 默认不同 → 不得合并。**

## 十二、第二轮新增的规则

16. **判据的收敛本身就是质量的一部分。** 判据改到没人能复述最终版本时，它就不再是判据，而是一段历史。要设停止条件。
17. **冻结判据 ≠ 冻结测量方式。** 判据语义 =「判什么」+「怎么测」+「拿什么比」；只冻结第一维，"不改判据"就是空话。
18. **冻结必须附「不覆盖清单」。** 判据说"我检查什么"，清单说"我不检查什么"；只交付前一半，缺口会随冻结变成默认。
19. **任何"不检查某物"的决定，都要说清"用什么替代它检查"。** 答不出替代物的，就不是例外，是漏洞。
20. **类别排除的自证义务**：这条正则**会不会命中所保护的对象**？答不出就不许加。
21. **只增不减的例外表 = 判据在慢慢失效。** 例外的计数必须打印（仅打印，禁止断言）。
22. **阴性对照必须常驻**，且要能证明"它真失效时会红"—— 用改 marker 的方式让对照条用**自己的消息**失败。
23. **守卫的守卫**：④ 与 ②a 的检测能力，没有任何用例证明它们能工作 —— 这是"断言空转"的递归版本。
24. **正面结论与负面结论走同一条事实核对。** 说不出出处的正面结论，与说不出出处的负面结论同等处理：不进报告。
25. **凡是「A 出现了 N 次」的说法，必须当场列出 N 个实例**；列不出来就写"印象"。
26. **拼装结论要逐段标出处**：一条由多次测量拼成的结论，每个子结论各带自己的出处。
27. **举例子论证时，例子本身也要通过它所在的那个上下文** —— 举完回头在代码里定位它一次。
28. **推翻他人的前提时，先查那个观测的出处** —— 规则与观测冲突时，第一动作不是选边。
29. **压缩人工判定面**：每加一条机械检查，就问一次"它能不能把某个人工判断吃掉"；能吃掉的就不该留在人的位置上。
30. **两条排除规则**：`缺陷豁免`（带撤销触发器：修复该缺陷的提交里同步删除）/ `类别排除`（按来源正则，无触发器，但必须写明排除的来源）。
31. **测试依赖生产代码改动时，先提交生产改动。** 否则历史里会留一个红的提交。
32. **`amend` 只允许在「未 push 且未被他人引用」时使用**；hash 一旦出现在他人消息里，就只能追加。
33. **跨文档指代用名字，不用序号** —— 同一序号在别处可能已被占用。
34. **结构性修复 > 统计证据。** 13 连绿在"修前 p≈1/4"下约 2.4%，但 flake 源自负载、各次不独立，**2.4% 是下界性质的支持，不是无 flake 的证明**。更强的证据是**失败模式已写不出来**（原 break 条件被移除）。连跑是旁证，不是主证。
35. **过期的"不覆盖"比漏写更糟。** 缺口被修好后，不覆盖清单必须同步删除对应条目 —— 否则读者会以为那条仍未被检查。
36. **清单是快照，批次是变更 —— 每批动手前必须重取快照。** 删除会重新分配"谁孤立了谁"，所以复核必须在**所有已合并批次之后**做，不能按单批推。
37. **两个检查抓两个方向**：`knip 集合 diff` 抓**名单外**变化（新死导出、duplicate 消失）；**重算 ④** 抓**名单内**漂移（"文件内自用" → "彻底没人用"）。只做前者，会把"该删的"做成"去 export"，然后被 `noUnusedLocals` 红。
38. **验证步骤本身也需要自检。** 重算 ④ 的脚本必须有词边界（`(?<![A-Za-z0-9_$])`）—— 否则 `AllianceConfig` 会被 `NpcAllianceConfig` 子串命中，得出"仍有 4 处引用"的错误结论。**这是 ② 的第 4 个盲区：匹配太松。**
   **后果是双向的**：漏加边界 → 假阳性（不敢删）；把名字敲短（`grep "AllianceConf"`）→ 漏命中 → **假阴性（错删）**。**后者更危险，因为它不报警。**
   **"守卫的守卫"有两种漏法**：前两次（`renderCount` 未执行、`errSpy` 未被断言）是**漏在调用**；这次是**检查执行了但算错了**，即**漏在实现**。同一个家族的两端。
39. **② 的四个盲区（grep 数的是"字符串出现"，引用关系只占其中一部分）**：① `React.lazy` 变量名与组件同名；② 符号名 == 文件名 → import 路径串命中；③ 注释/文档里提到该名字（**随注释变多只会更多**）；④ 子串匹配（漏加词边界）。
40. **KAT（已知答案自验）用于验"算得对不对"**：喂人工可数的样本，看脚本是否报同一个数。实测 3/3 通过，并暴露**朴素计数在带子串的名字上系统性偏高**（`AllianceConfig` 5 vs 3、`Hero` 4 vs 3）。
   - **差值（边界计数 − 朴素计数）= 该批符号里"子串干扰"的规模**，可作删除类批次的前置读数
   - **KAT 的边界**：它能验"实现与预期一致"，**验不出"预期本身对不对"** —— 路径串里的文件名（`'@/.../WorldMap'`）在文本层面与真实引用无法区分，属**设计盲区，不是实现缺陷**，只能人工判 + 记录。
41. **有两组对照，尺度不同、目的不同，不可合并成一条规则。**
   - **指标对照（同尺度，两数必须相等）**：数"全部 `shared → features` 边"，一条按语法（`from|import(|require`），一条按裸子串 `"@/features/"`。**不相等 = 有没覆盖的写法**（双引号 / Prettier 折行 / `require`）。
   - **改写对照（异尺度，与指标无关）**：数"被移动项的**具体路径片段**"有多少个引用点，与改写脚本命中数比对。**相等 = 没漏改**。这些引用点里多数是 `features` 内部引用，**本来就不是反向边**。
   - **把两组混起来会出事**：有人会拿"10 个引用点"和"2 条反向边"去比，然后以为出了错。**每组只和它自己比。**
42. **口径界定 ≠ 例外。** 口径界定（不在范围内，如 `tests/`）只需写进定义 + **每次打印被排除的条数**；例外（在范围内被豁免）必须说清**用什么替代它检查**。
43. **移位与改名不同批。** 一次提交里同时有"文件移位"和"文件改名"，出问题时无法归因到是哪一种改动引起的。
44. **被引用次数 ≠ 反向边收益。** `BattleTypes.ts` 被 6 个文件引用，但其中 5 个在 `features` 内部，只有 1 个在 `shared` —— 所以下沉的边收益是 **1**，不是 6。**估计收益要数"被 `shared` 引用的条数"，不是总 importers。**
45. **提交标题放不下完整路径时，标题只写文件名 + 目标目录，完整路径进正文。** `commit-msg` 钩子限制冒号后 `.{1,50}`，B4 这类"路径 A 上移到 路径 B"的标题必然超长（中文按 1 字符算）。**不跳钩子、不用 `--no-verify`。**
46. **预期值是单值；不确定项单独列。**
   - **收益**（凭据：反向边数）与**性价比**（凭据：改写点数 ÷ 消边数）是两个判断，不可混写
   - 把"性价比差"写成"结果不确定"，读者会以为要改预期 —— 这是把**计划中的判断题**和**已定的执行项**混进同一段
   - **实测（非估算）**：B4 全程 **68 处 import 改写 / 12 条消边 = 1:5.7**。分步最贵的是 `Hero.ts`（26 改写换 3 边 = 1:8.7，因它被 25 个文件引用）。估这类工作量应按"改写点数"，不按"消边数"
47. **报告里的每个数字必须标来源：实测（附命令）还是估算。** 估算值不得进结论表，也不得写进规则原文 —— 因为规则原文会被复用。
   - 本轮我（主理人）在这一点上错了三次：`10KB 物品表`（实为 2,320 B）、`LootBox 再改 6 处`（实为 3 处）、`B4 固有税 1:4`（实为 1:5.7）
   - **三次都是"用一个没核过的量级数去支撑一个正确判断"** —— 危险不在结论，在它会被下一个人照着用
48. **口径变更时，历史数字必须整体重算或整体标注"旧口径"，不得跨口径拼成一条曲线。**
   - 实例：B4 前四步用的是旧命令（只认 `from`），后三步换成语法+子串双数，两段拼成 `12 → 9 → 7 → 5 → 3 → 2 → 1 → 0`，**看起来最平滑，恰是最难发现的错**
   - 不光要问"这个数准不准"，还要问"**这条曲线上的每一个点，是不是同一把尺子量的**"
   - 若必须拼接，**逐行标注口径来源**，并写明"重算值成立所依赖的条件"
49. **口径界定的排除项要当检查项用。** `tests/` 内那 1 条不计入指标，但**每次必须打印** —— 哪天它变成 2、3 条，就说明有测试在往 `shared` 里塞 `features` 依赖。**只打印不检查，口径会静默失效。**
50. **任何"对集合全体成立"的断言，必须同时断言集合非空。** 否则空集让它恒真 —— **断言空转，看起来是绿**。
   - 形态不止 `⊆`：**`⊆` / `every()` / `!some()` / `filter().length === 0` 全部属于这一族**
   - 实例：`favicon 请求集合 ⊆ {'/favicon.svg'}` 在"浏览器本次没发起 favicon 请求"时为真；AC-09 的 `illegalFavicon.length > 0` 判红同样在空集上真空转
   - 处置：空集必须**显式报为"未验证"，不得计入通过**；并另配一条在真实产物上验证采集通路
   - **只按 `⊆` 去 grep 会漏掉 `every` 写法** —— 这条规则要按"形态族"检，不能按单个符号检
51. **复述规格时必须逐条带状态标记（✅已提交 / ⚠️部分 / ❌未做）。** 触发点不是"写进文档时"，而是**"把规格复述给对方时"** —— 因为读者只会记住那张表，下一手会把"打算怎么做"当成"已经做到"。
   - 实例：交付说明先写了四条规格，而代码只满足其中一条的一部分；`e54b378` 补齐后才一致
   - **文档与代码不一致，比两边都缺更坏** —— 读文档的人会以为已经做到
52. **静默修正的反面不是"报错"，而是"让错误在结构上无法表示"。**
   - `--path` 静默忽略 → 量的是 `/`、报告的是 `/reports` 的意图 → **数字正常，对象错了**
   - **手维护的差集清单** → 清单烂了没人知道 → `runtime = static + Σchunk` 依然"成立"，**门禁永远绿**
   - 后者最危险，因为**它不会报错**。所以恒等式里的 `Σ启动期chunk` 必须**算出来**（运行时请求集合 − 静态解析集合），不能手写维护 —— **这不是省事，是让"清单腐烂"这个失败模式在结构上不可能发生**
53. **任何"两者应当相等/不等"的分叉断言，必须同时断言"两者本来会不同"的机制仍然存在。** 否则机制消失后，断言会静默恒真。
   - **这一族的统一表述**：**断言的作用域，大于它想覆盖的场景。**
     - 正向说法："断言说了真话，但说的不是我们想问的事"（例：`getSnapshot` 返回同一个空数组，`Object.is` 依然成立）
     - 反向说法："**断言说了一件我们想问的事，但在没有被问到的输入上恒真**"（例：`renderCount <= 2` 在 0 次渲染时为真 —— 它问的是"渲得太多次吗"，而在"没渲染"的世界里答案也是"否"）
     - **两者共同点都是作用域过大；补法也一样：把作用域收窄到"机制存在"的前提下**
   - 实例（A4）：`结算与延迟无关` 若某天修复速度被调成 0，两条路径算出的值相等 —— **断言永远绿，且绿得毫无意义**。所以必配前提用例「城池在战斗中确实修复、`T1 的 cur > 冻结值`」
   - **一个因为前提消失而恒真的断言，比没有断言更坏** —— 它会一直报告"已守住了"
   - 这是规则 50（集合非空）的推广：对象从"集合"换成"**前提**"，覆盖面更宽
   - 全量审计（17 文件 / 81 用例）结果：**缺前提 12 项，分布在 7 个文件**，归为四族：
     | 族 | 形态 | 数量 |
     |---|---|---|
     | **同空恒真** | `Object.is(a,b)` / `a?.x === b?.x` 两侧同时 undefined 时相等 | 3 |
     | **空集恒真** | 集合为空 ⇒「没有违规项」恒成立 | 4 |
     | **未观测恒真** | 观测对象根本没被观测到（没渲染 / 计数 0） | 2 |
     | **分母为 0** | 计数器全为 0 时，等于 0 的那个看不出异常 | 1 |
   - **判据**：这 12 项**没有一项是当前坏的**，全部为绿且实现正确。**它们的价值是"将来某人改坏了而断言不响"** —— 若用"能抓到几个现有 bug"评估，这批会得 0 分
   - **补强已完成（`0c613a2`）**：11 项补上（#5 属结构问题，见下），6 文件 +47 行纯加断言，体积中性
     - **变异证据**：把 `getSnapshot` 改成"永远返回同一个空数组"——**原来的 `Object.is(first, second)` 断言会通过**（同一引用，引用确实稳定，但对象是空的）；新加的前提断言在**第 60 行**红。**说明那个洞是真的**
     - 11 条新前提在当前实现下**全部为真** —— 若有一条为假，说明那个机制现在就已经坏了
   - **#5 未做，登记为已知结构限制**：`snapshot.mount.test.tsx` 的 FIRST 断言依赖 React 的 warn-once 通道，同进程内前序用例可能消耗它 → 该断言在非首个违规用例上可能空转（现由 SECOND 抛错与 `renderCount` 兜底）。**解除条件**：该文件出现第三条依赖 warn-once 的断言，或 SECOND 被改动，必须做进程隔离
   - **静态检查的形态（记账，本轮不做）**：不做"断言与守卫配对"（断言对象名与守卫对象名不一定一致，纯文本判不了），改做**"同用例内是否至少存在一条 `> 0` / `toBeGreaterThan(0)` / `toBeDefined` / `toHaveLength(n>0)` 形态的断言"**。代价是有可能"守的不是那个对象"的假阴性 —— **宁可漏检，不可误报：误报会让这条检查工具本身被关掉**
54. **容差的合法性，取决于"它吸收的分量是否与代码无关"。**
   - 抖动实测 = 0 B ⇒ **现在加容差，只会吸收"与代码有关的分量"，也就是把真回归吞掉**
   - 所以"因为怕抖动所以先加容差"是错的顺序：**先证抖动存在，再谈容差**；抖动为 0 时，容差不是保守，是主动把门禁变钝
   - **加容差必须同时写"解除条件"**（例如「连续 N 次构建抖动为 0 即移除」）—— 否则它会从"应对已知抖动"退化成"永久钝化"。
     **理由**：容差一旦存在，**没有任何机制会提醒你它已经不需要了**。这和 `#5`（warn-once 空转）是同一个形状：**一个曾经有理由、后来理由消失、却仍然生效的东西**。本轮已写了两处解除条件（`#5`、阶段二"待重新推导"），它们能立住靠的就是"什么情况下这条失效"被写下来 —— **容差不写解除条件，会成为第三处"没有出口的已知限制"**
55. **"我担心的"不能写成"已成立的"。** 两个实例：
   - 从"余量只有 0.77%"直接跳到"很快会用完" —— **少了斜率**（实测 +3 B / 三批，约 280 批才耗尽）
   - 从"可能有抖动"直接跳到"零改动也可能翻红" —— **少了实测**（实测 5 轮抖动 = 0）
   - 共同点：**省略了一步验证，而那一小步恰好决定"是不是威胁"**。纠正方式也一样：**给出能让结论落地的那个量**
   - 带"如果"的假设仍会被当成"已考虑过的风险"写进计划，**所以必须显式作废，不能留着**
56. **清单类交付誊完后，必须核"总数 = 逐项数"。**
   - 实例：审计表 12 项，减去属结构问题的 #5 应为 **11 项**，而交付清单只列了 **10 个编号** —— 漏了 #10。**数一下就能当场发现**
   - **这个动作比"仔细一点"可靠，因为它有判据**
   - 并且：**发现不一致时，要按"清单缺项"处理，不是按"执行偏差"处理** —— 前者导出"清单需要复核"，后者只导出"下次照清单"，而漏项在**誊写**环节，下次誊还会漏
57. **"端点相等"型断言无法区分单调曲线与阶跃 —— 要在中段和零点各取一个样。**
   - 实例（G1a）：曲线从"0→cap 线性"被改成阶跃后，`diff(score 0, 2500) === cap` **依然成立**；抓到它的是 `A2`（中段 ≈ cap/2）与 `G`（`score 0→1` 连续）
   - **推论**：任何"首尾两点"就能满足的断言，对**形状**是盲的
   - **同一个盲区在文档里也成立**：给曲线写说明时**至少取三个采样点（起点 / 中段 / 饱和点）** —— **两个点只够画一条直线，三个点才看得出形状**。G1a 的"激励方向反了"就是这样被发现的：为了写"差多少"必须把 `score 0/1/750` 都算出来，**只算"上限"那一个点，永远看不到 0→1 的跳变**
58. **"别改回去"是威慑，"改回去哪条会红"才是路标。** 注释里写清"违反这条判据时哪条断言会失败"（例：`G` 守着连续性、`A2` 守着中段、`A` 区分不了形状）—— 因为下一个人改坏时要找的不是训诫，是失败的那一行。
59. **取样点与阈值必须跟随常量，不能写死。** 这是规则 57 的反方向：
   - 57 说**取样点太少会盲**（端点相等抓不住阶跃）；这条说**取样点写死了会假红**
   - 实例（G1a 审计）：`A2` 断言 `score 750 → cap/2`，把"饱和点的 1/2"写成了字面量 `750`；改 `LINEAR_CAP` 到 1000 或 2000，**三次都是纯常量改动，两次红** —— 红的原因不是形状坏了，是"中段"移走了
   - 实例二：`G` 的阈值 `cap/1000` 是比例，而左边是取整后的整数 —— `cap ∈ [750, 999]` 时 `contrib(1)=1 > cap/1000`，**形状正确却假红**，且未来的解释会是"加了大城"而不是"阈值写死了"
   - **判据**：改常量后若形状断言红，**先核对"取样点与阈值有没有跟着常量走"，再怀疑形状**
   - **同一个盲区有三个载体，补法都是"让采样点跟着被测对象走，而不是写死"**：
     | 载体 | 写死的形态 | 正确写法 |
     |---|---|---|
     | **断言** | `score 750`（其实是 `LINEAR_CAP/2`） | 取 `LINEAR_CAP / 2` |
     | **文档** | 只写端点两个数 | 写起点 / 中段 / 饱和点 |
     | **阈值** | 裸比例 `cap/1000`（对取整整数） | `max(1, cap/1000)` |
   - **一句话**：**任何写死的采样点或阈值，都会在被测对象变化时给出错误的结论 —— 要么盲、要么假红**
   - **可机检的形态**：断言两边"一边离散、一边连续"时（左：`round/floor/length/count`；右：`cap*ratio / 1000`），**必然存在一条错位带**。
     **判据：比例阈值的下限不能是 0，必须有一个"至少 1 个量化单位"的地板** —— 即 `max(1, cap/1000)` 里的那个 `1`
   - **修复已落（`4c60fa9`）**：`A2` 取样改为 `LINEAR_CAP/2`；`G` 阈值改为 `max(1, cap/1000)` 且取样扩到 **7 个量级**（760/2000/5000/7500/8000/9990/12000）—— 只改阈值不改取样，"修假红的补丁"本身无法被证伪
     - **决定性证据**：把阈值退回裸比例后 `max=7500` 立刻红（`跳变 1 > 0.75`），**证明那条错位带真实存在、且新阈值抹平了它**。没有这一步，"修假红"只是自我声明
     - **`cap=800` 是错位带正中间**：`contrib(1)=1 > 0.8`（裸阈值）→ 形状正确却红；地板 `max(1, …)` 刚好接住。**所以地板必须是"1 个量化单位"，不能更小**
     - **常驻取样 > 一次性验证**：一次性改完还原，**证据在跑完那一刻就消失了**；写进测试则每次都在证伪。代价是 G 从 2 次断言变 14 次（7 量级 × 2），耗时仍个位数毫秒
     - **采样点要留在"区间"里，不是留在"边界"上**：错位带是 `cap ∈ [750, 999]`，**若只留 750 与 999 两个端点，中间那段仍无人管**。**边界采样能证明"带存在"，区间采样才能证明"带被抹平"** —— 两者都要，但只有后者能防止"修了一半"
60. **凡是带数值的约定，把「端点 / 中段 / 参数被改动后」三个场景都算一遍。** 三者里任意一个没算，剩下的两个都会给出"看起来通过"的结论。
   - 本轮最后三次修正**全部来自"把数字真的算了一遍"，没有一次是"看代码看出来的"**：
     | 算了什么 | 发现了什么 | 修法 |
     |---|---|---|
     | `score 0 / 1 / 750` | 阶跃（打一下 = 最大收益） | 换曲线 |
     | `cap ∈ [750, 999]` | 比例阈值与取整结果的错位带 | 加地板 |
     | `LINEAR_CAP = 1000 / 2000` | 取样点写死成 750 | 跟随常量 |
61. **「已接入 / 已生效」这类完成态断言，必须同时给出可执行载体和一条复现命令。**
   - 实例（AC-05）：本轮文档把它标成「✅ knip 已接入 verify，`src` 内已归零」。实测 `verify` 链是 `lint → lint:style → format:check → typecheck → assets:check:strict → test:coverage → build` —— **没有 knip**；CI 只跑 `npm run verify` ⇒ **knip 从未被任何自动化执行过**。
   - **为什么两轮都没人发现**：✅ 是一个**纯文本标记**，它与"载体真的存在"之间没有任何机械联系 —— 谁能写就能写 ✅。同一份文件里第一轮的表标的是「⚠️ 未写断言」，**两个状态并存了两轮**，靠人读才撞出来。
   - **判据**：写 ✅ 的地方，必须能一句话答出"跑哪条命令能证明它"。答不出来就只能标 ⚠️。
   - **结构消灭**：把它变成 `verify` 链里的一环（`… → typecheck → knip → assets:check:strict → …`）—— 此后 ✅ 不再由人声明，而由 `npm run verify` 的退出码决定。
   - **推论（更狠的一条）**：**"已归零"这类数量断言，必须同时写清"清零发生在哪个提交"和"什么拦着不让它涨回去"。** 只写数字不写守卫，数字会在下一次提交时悄悄失效 —— G1a 就是在我写完"`src` 内归零"之后立刻造出 3 个新死导出的。
62. **工具报 `unused export` 说的是"没人从模块外引用"，不是"这段代码是死的"。**
   - 实例：`scripts/perf/budget.mjs:74` 的 `ledgerSum` 被同文件 `:81` 调用、`checkLedgerInvariant`（`:80`）被 `:150` 调用 —— 它们**在跑**，只是不该 `export`。
   - **后果**：按字面理解去"清理死代码"，会删掉正在用的函数。
   - **判据**：先看它在本文件内是否被调用。**是 → 去掉 `export` 关键字；否 → 才是真死代码。**
   - **反例（knip 的天然盲区，已登记）**：`scripts/git/commit-msg.mjs` 由 `.git/hooks` 调用，不被任何代码 `import` ⇒ knip 报 unused file，但它**不是死文件**。**凡"由外部进程调用而非模块 import"的脚本，knip 都会误报。** 本轮的 `ignore: ["scripts/**"]` 恰好覆盖了它 —— **结果对、理由错**。若将来某个 `scripts/` 文件改成被 `src` 引用，这条 ignore 会掩盖问题。
   - **与规则 61 的关系**：61 说"声称要能被复现"，62 说"复现工具本身有盲区"。**二者合起来才是完整判据：门禁可信，但它说的每一个词都要翻译成人话再执行。**

### 关键设计

| 项 | 内容 |
|---|---|
| **退出码三分** | `0` 通过 / `1` 超预算或 favicon 断言失败（代码问题）/ `2` 无法判定（无运行时数据、缺浏览器、口径不自洽） |
| **账本不变量** | `thresholdBytes === baselineBytes + Σ allowed[].deltaBytes` → `112640 === 111779 + 861`。**861 B 的余量必须是一条显式记录**；账本对不上返回 `2`（配置错）而非 `1`（代码错） |
| **恒等式** | `runtime = static + Σ启动期chunk`；**差集由「运行时请求集合 − 静态解析集合」算出来并每次打印**，不手写维护；不成立 → `exit 2` |
| **路径钉死** | 硬编码 `/`，不提供 `--path`；断言 `finalPath === '/'`，否则 `exit 2`。注释写明 `/reports` 今日 113,556 B 超 916 B —— **这是路由重量，不是首屏回归** |
| **CI** | 三步且有顺序：Chrome 存在性检查 → **门禁自验** → 体积门禁。自验在前，因为门禁坏了先跑门禁只会得到无法解释的红 |

**`perf:budget` 未并入本地 `npm run verify`** —— 本地 verify 不该强依赖 Chrome；**合并门槛由 `verify.yml` 承担**。

### 余量的两种威胁，性质不同

余量 `861 B` 会被两种东西吃掉，**但只有一种是真威胁**：

| 威胁 | 实测斜率 | 判断 |
|---|---|---|
| **正常代码增长** | A4 +0、AC-08 前提 +0、幂等批 +2、再 +3 → **+3 B / 三批** | 按此斜率约 **280 次同量级改动**才耗尽 —— **不是眼前的威胁** |
| **同码重复构建的字节抖动** | **实测 = 0 B**（5 轮完整重建，`runtime` 恒为 `111,782`，`dist` 指纹恒为 `9f429bf54cf5`） | **证伪** —— 该担心不成立 |

> **抖动 = 0 意味着这个门禁是"确定性函数"**：同一份产物永远给同一个数。**红就是红，不需要先排除"这次运气不好"。**
> **换句话说：抖动为 0 才让"冻结线"这个概念成立 —— 否则冻结的不是代码，是骰子。**

**余量 858 B 是实打实可用的 858 B，不需要预留抖动容差。** 真正在消耗余量的是代码（约 1 B/批次），按此斜率**不是近期威胁**；放宽账本暂时**不需要**成为常用通道。

> 把"余量会被正常迭代吃掉"当成主要风险是**方向错的**：斜率数据显示它极慢；**真正要先量的是抖动**。做法：同一提交重复构建 5 次，`runtime` 必须逐次相等；若不等，冻结线现在就该配一个抖动容差，而不是等它红一次再讨论。

## 十七、A4 修复：战报前值 = 战斗实际采用值（已完成 `aa5c188`）


- **断言不复制生产公式**：写 `after === frozen - dmg` 会把公式抄进测试，公式一改就假红假绿。要守的不变量是「**结算与结算延迟无关**」。

### 口径内部矛盾，被实现逼出来

原始口径三条 —— **贡献占扣减总额 20–30%** / **前段线性** / **硬顶 max×10%** —— **描述的是两种形状，不可同时满足**：

| 形状 | 打一下（score=1） | 技能区分度 | 激励方向 |
|---|---|---|---|
| **率线性**（有 20% 基线） | **+50～76** | 25 点 | **反的** |
| **0 → cap 线性**（采纳） | **≈0** | **76 点（3 倍）** | 正 |

> **"率线性"下玩家最划算的动作是"随便点一下"** —— 这不是"差距小"，是**设计在奖励错误行为**。

**新口径**：`contribution = round(cap × min(1, eff/1500))`，`cap = floor(max×10%)`，`eff = score ≤ 1500 ? score : 1500 + (score−1500)×0.5`。
**「20–30%」作废**（与"前段线性"不可同时满足）；打满时约占本次扣减 **15%–23%**，**不打为 0**。

### 结构消灭：签名里去掉 `dmgBase`

`computeSiegeContribution({ score, max })` —— **把 `dmgBase` 留在签名里，下一个调参的人会本能地把它乘回去，于是退回旧形状。去掉参数，比在注释里警告更有效。**（同"让 `claimKeyRef` 消失"）

**后果（口径问题，需设计确认）**：贡献变成**绝对量**，所以**弱攻击受益相对更大、强攻击相对更小**。若设计要的是"越强越划算"，必须先定"cap 是绝对值还是比例"—— 那是口径变更，不是调参。
